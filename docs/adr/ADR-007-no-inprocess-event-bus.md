# ADR-007: 인프로세스 이벤트버스(ApplicationEventPublisher 등) 미도입

## Status
Accepted

## Context
Spring은 `ApplicationEventPublisher`와 `@TransactionalEventListener`를 통해 애플리케이션 내부에서 이벤트 기반 디커플링을 지원한다. 이는 도메인 이벤트가 많고 발행자-구독자 관계가 복잡할 때 유용하다.

그러나 이 프로토타입에서 발생하는 이벤트 종류는 2~3개 수준(예: 관계 시작, 하루 종료, 턴 확정 정도)으로 매우 적다. 이런 규모에서 이벤트버스를 도입하면:

- 이벤트 발행/구독 등록 코드, 리스너 클래스 등 보일러플레이트가 늘어남
- 실행 흐름이 간접화되어(발행 → 리스너 탐색 → 실행) 디버깅과 코드 추적이 오히려 어려워짐
- `@TransactionalEventListener`의 트랜잭션 경계/타이밍(BEFORE_COMMIT, AFTER_COMMIT 등) 이해 비용이 이벤트 개수 대비 과도함

## Decision
`ApplicationEventPublisher`, `@TransactionalEventListener` 등 인프로세스 이벤트버스를 도입하지 않는다. 이벤트에 해당하는 로직은 서비스 메소드 직접 호출로 처리한다 (예: 관계 시작 시 캐릭터 초기화 로직은 `RelationshipService`가 `CharacterService`를 직접 호출).

## Consequences

### 긍정적 영향
- 실행 흐름이 코드를 따라가는 것만으로 명확하게 추적 가능 (간접비 없음)
- 트랜잭션 경계가 메소드 호출 스택과 일치하여 이해하기 쉬움
- 이벤트버스 관련 보일러플레이트(이벤트 클래스, 리스너 클래스, 등록) 제거로 개발 속도 향상

### 부정적 영향 / 트레이드오프
- 서비스 간 결합도가 이벤트버스 방식 대비 높아짐 (직접 의존성)
- 향후 이벤트 종류가 늘어나거나 다대다 발행-구독 관계가 필요해지면 리팩토링 필요
- 여러 서비스가 동일 이벤트에 반응해야 하는 시나리오가 생기면 직접 호출 체인이 길어질 수 있음

### 재검토 조건
- 이벤트 종류가 유의미하게 늘어나거나(예: 5개 이상) 다대다 발행-구독 구조가 필요해지는 시점
