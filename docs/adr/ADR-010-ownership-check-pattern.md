# ADR-010: 리소스 접근 엔드포인트의 소유권 검증 패턴

## Status
Accepted

## Context
Phase 4 REVIEW + SECURITY 검토(`docs/security/2026-08-14-idor-ownership-check.md`)에서 CRITICAL 등급 IDOR(Insecure Direct Object Reference) 취약점이 발견됐다. 관계(UserCharacter, UC) 리소스에 접근하는 REST 3개 엔드포인트(`GET /api/relationships/{ucId}`, `POST .../message`, `POST .../end-day`)와 WebSocket 1개 경로(`SEND /app/chat/{ucId}`)가 전부 `ucId`만으로 리소스를 조회하고, 요청자가 실제 소유자인지 전혀 검증하지 않았다.

이 프로젝트는 ADR-003에 따라 `X-Player-Id` 헤더 기반 경량 식별을 쓴다. 이 헤더는 클라이언트가 임의로 설정 가능하므로, "내 `X-Player-Id`로 남의 `ucId`를 지정해 요청"하는 시나리오를 막는 책임은 전적으로 서버(리소스 조회 계층)에 있다. `ucId`가 auto-increment PK라 순차 추측이 쉬운 점도 위험도를 높인다.

앞으로 추가될 모든 리소스 접근 엔드포인트(예: 향후 다른 도메인의 소유자 기반 리소스)에서 동일한 실수가 반복되지 않도록, 검증 패턴과 실패 시 응답 방식을 아키텍처 결정으로 고정할 필요가 있었다.

## Decision
**리소스를 특정 플레이어가 소유하는 모든 접근 엔드포인트(REST + WS)는 다음 패턴을 따른다.**

1. 요청자는 REST의 경우 `@CurrentPlayer Player player` (기존 `CurrentPlayerArgumentResolver`, ADR-003), WS의 경우 STOMP `CONNECT` 프레임에서 `StompAuthChannelInterceptor`가 검증해 세션에 바인딩한 `playerId`로 조회한 `Player`를 사용한다. 클라이언트가 별도로 보낸 소유자 식별값(예: body의 playerId 필드)은 신뢰하지 않는다.
2. 서비스 계층에서 리소스(`ucId` 등)를 조회한 뒤, `resource.getPlayer().getId().equals(player.getId())`를 검증한다. 이 검증은 컨트롤러가 아니라 서비스 계층에 둔다 — 서비스가 직접/간접(WS 등 다른 어댑터에서) 호출되는 모든 경로에서 빠짐없이 적용되게 하기 위함이다.
3. **불일치 시 응답은 리소스가 존재하지 않을 때와 동일하게 처리한다.** UC 도메인의 경우 `404 RELATIONSHIP_NOT_FOUND`. 즉 "존재하지만 권한 없음(403)"과 "애초에 존재하지 않음(404)"을 구분하지 않는다.
4. WebSocket 경로는 REST와 동등한 보호를 받아야 한다 — `CONNECT` 프레임 자체에서 `X-Player-Id`를 검증해 세션에 바인딩하고, 이후 메시지 처리 시 이 세션 값을 기준으로 동일한 서비스 계층 소유권 검증을 통과해야 한다. WS 전용 우회 경로를 만들지 않는다.

## Rejected Alternatives

### 대안 A: 소유자가 아니면 403 Forbidden 반환
리소스가 존재함을 그대로 인정하고, 접근 권한만 없다는 의미로 403을 반환하는 방식. REST 시맨틱상으로는 더 정확해 보이지만 기각했다.

**기각 사유**: 403은 "이 ID는 존재하지만 너는 볼 수 없다"는 사실을 그대로 노출한다. `ucId`가 순차 추측 가능한 PK이므로, 공격자가 `ucId`를 순회하며 200/404(없음) vs 403(있지만 남의 것)을 구분할 수 있게 되면 존재하는 `ucId` 전체를 열거(enumeration)할 수 있다. 이는 그 자체로 정보 노출이며(다른 플레이어가 얼마나 많은 관계를 만들었는지, 최신 `ucId`가 어디까지 발급됐는지 등을 추정 가능), 이후 다른 취약점과 결합될 공격 표면을 넓힌다. 이 프로젝트는 정식 인증(ADR-003 기각)조차 두지 않은 경량 식별 체계이므로, 열거 방지를 통한 방어 심도(defense in depth) 확보가 더 중요하다고 판단했다.

### 대안 B: 컨트롤러 계층에서 AOP/인터셉터로 일괄 검증
`@RequireOwnership` 같은 커스텀 애너테이션 + AOP로 모든 컨트롤러 메서드에 선언적으로 소유권 검증을 강제하는 방식.

**기각 사유**: 현재 소유권 검증 대상 엔드포인트가 4개뿐이고, 리소스 타입(UC)과 소유자 필드(`player`) 조회 경로가 서비스마다 다를 수 있어 범용 AOP 규칙을 짜는 비용이 이득보다 크다고 판단했다. 대신 이 ADR로 "서비스 계층에서 명시적으로 검증한다"는 패턴을 코딩 컨벤션으로 문서화하고, 신규 엔드포인트 작성 시 이 문서를 참조하도록 `docs/PROJECT_CONVENTIONS.md`에 명시하는 쪽을 택했다. 엔드포인트 수가 늘어나 반복 실수가 잦아지면 재검토한다.

## Consequences

### 긍정적 영향
- IDOR류 취약점이 "리소스 존재 여부 조회 → 소유권 비교 → 없으면 동일한 404"라는 하나의 명확한 패턴으로 코드베이스 전체에 일관 적용된다.
- REST와 WS가 같은 검증 경로(서비스 계층)를 공유하므로, 어댑터를 추가해도(예: 향후 gRPC, 배치 잡 등) 소유권 검증을 다시 발명할 필요가 없다.
- 403 대신 404를 씀으로써 `ucId` 열거를 통한 정보 노출 표면을 줄인다.

### 부정적 영향 / 트레이드오프
- 정당한 사용자가 실수로 남의 `ucId`를 입력했을 때도 "권한 없음"이 아니라 "존재하지 않음"으로 보이므로, 프론트엔드 에러 메시지가 실제 원인(오타/잘못된 링크 vs 진짜 없음)을 구분해 안내하기 어렵다. 프로토타입 단계에서는 감수 가능한 트레이드오프로 판단.
- 서비스 계층마다 소유권 검증 코드를 개별적으로 작성해야 하므로(AOP 미사용), 신규 엔드포인트 작성 시 검증 로직을 빠뜨릴 여지가 여전히 남는다 — 코드 리뷰/REVIEW 단계에서 체크리스트로 보완해야 한다(`docs/PROJECT_CONVENTIONS.md` "인증/인가" 섹션 참조).

### 재검토 조건
- 소유권 검증이 필요한 리소스/엔드포인트 수가 유의미하게 늘어나 반복 누락이 실제로 발생하는 시점 — 대안 B(AOP화) 재검토.
- 정식 인증 체계(ADR-003 재검토 조건)로 전환되는 시점 — 소유권 검증을 인증 프레임워크(예: Spring Security의 `@PreAuthorize`)로 이전할지 재검토.
