# ADR-003: 익명 X-Player-Id(UUID) 헤더 기반 경량 인증

## Status
Accepted

## Context
정식 로그인 체계(Spring Security + JWT, OAuth 등)를 도입하면 회원가입/로그인/토큰 갱신/비밀번호 관리 등 상당한 구현 비용이 발생한다. 이 프로토타입은 다음 조건을 가진다.

- 심사자가 별도 회원가입 절차 없이 즉시 플레이할 수 있어야 함 (진입 장벽 최소화가 최우선)
- 결제, 개인정보 등 민감 정보를 다루지 않음
- 1주일이라는 짧은 개발 기간

정식 인증 체계는 이 조건에서 얻는 이득 대비 구현/검증 비용이 과도하다.

## Decision
클라이언트가 최초 접속 시 UUID를 생성해 로컬에 보관하고, 이후 모든 API 요청에 `X-Player-Id` 헤더로 이 UUID를 전달하는 경량 식별 방식을 사용한다. 서버는 이 헤더 값을 신뢰 가능한 플레이어 식별자로 취급하며, 별도의 비밀번호/토큰 검증을 수행하지 않는다.

- 헤더가 없는 요청은 `AUTH_MISSING_PLAYER_ID`(401)로 거부한다.
- Spring Security, JWT 등 정식 인증 프레임워크는 도입하지 않는다.

## Consequences

### 긍정적 영향
- 회원가입/로그인 UI와 백엔드 인증 플로우 구현이 전부 불필요해져 개발 속도가 크게 향상됨
- 심사자가 앱 진입 즉시 플레이 가능
- 세션/토큰 관리, 토큰 갱신 로직이 없어 클라이언트 구현도 단순해짐

### 부정적 영향 / 트레이드오프
- `X-Player-Id`는 클라이언트가 임의로 조작 가능하므로 사실상 인증이 아닌 식별 수준의 보안만 제공함
- 타인의 UUID를 알면(또는 추측하면) 그 플레이어인 것처럼 요청을 보낼 수 있음 — 민감 정보/결제가 없는 프로토타입 범위에서만 허용 가능한 리스크
- 클라이언트 로컬 스토리지가 삭제되면 진행 상황 복구 수단이 없음 (계정 복구 개념 자체가 없음)
- 정식 서비스로 전환 시 반드시 정식 인증 체계로 마이그레이션 필요

### 재검토 조건
- 프로토타입이 실제 운영 서비스로 전환되는 시점 (필수 재검토)
- 결제, 개인정보 등 민감 데이터를 다루게 되는 시점
