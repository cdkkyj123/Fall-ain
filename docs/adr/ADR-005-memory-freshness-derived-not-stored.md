# ADR-005: 기억의 신선도(freshness)는 조회 시점 파생 계산

## Status
Accepted

## Context
게임 내 "기억"(유저가 되짚을 수 있는 Canon 사실)에는 신선도 개념이 있다: ACTIVE(최근에 언급/터치됨) → FADING(시간이 지남) → FADED(오래되어 잊혀짐). 이 신선도는 되짚기 시 판정과 UI 표시에 영향을 준다.

전통적인 구현 방식은 신선도 상태를 DB 컬럼으로 저장하고, 배치 작업(스케줄러)이 주기적으로 상태를 전이시키는 것이다. 그러나 이 방식은 다음 복잡도를 수반한다.

- 배치 스케줄러 인프라 구축 및 트리거 관리
- 상태 전이 타이밍의 정확성 보장 (배치 주기와 실제 게임 진행 사이의 간극)
- 상태 불일치 가능성 (배치가 늦게 돌면 실제로는 FADED인데 DB상 FADING으로 남아있는 등)

1주 일정의 프로토타입에서 이런 복잡도를 감당할 이유가 없다.

## Decision
신선도 상태를 DB에 별도 컬럼으로 저장하지 않는다. 대신 각 기억(Memory) 엔티티에 `lastTouchedDay`(마지막으로 언급/되짚어진 게임 내 일차)만 저장하고, 조회 시점에 다음과 같이 파생 계산한다.

```
daysSinceTouch = currentDay - lastTouchedDay
freshness = daysSinceTouch에 따른 구간 매핑 (ACTIVE / FADING / FADED)
```

상태 전이를 위한 배치 작업이나 스케줄 트리거는 도입하지 않는다.

## Consequences

### 긍정적 영향
- 상태 전이 트리거 메커니즘이 아예 필요 없어짐 (스케줄러, 배치 작업 불필요)
- 항상 최신 `currentDay` 기준으로 정확한 freshness를 계산하므로 상태 불일치 문제가 원천적으로 없음
- 구현이 순수 함수(pure function)로 단순화되어 테스트가 용이함

### 부정적 영향 / 트레이드오프
- 조회할 때마다 계산 비용이 발생함 (다만 단순 정수 뺄셈 수준이라 실질적 성능 영향은 미미)
- freshness 값 자체로 DB를 필터링/정렬하는 쿼리는 불가능하며, 애플리케이션 레벨에서 계산 후 필터링해야 함 (조회 대상 규모가 작아 문제되지 않음)
- 구간 매핑 기준(ACTIVE/FADING/FADED 경계값)이 변경되면 과거 데이터 재계산 없이 즉시 전체 데이터에 소급 적용됨 (의도된 동작이나 유의 필요)

### 재검토 조건
- 기억 데이터 규모가 커져 조회 시점 계산 비용이 유의미해지는 시점
