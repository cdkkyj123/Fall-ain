# ADR-006: 대화 턴 예산은 pending 예약 → 확정 2단계 커밋

## Status
Accepted

## Context
유저는 하루에 8턴의 대화 예산을 가진다. 초기 설계안은 유저 메시지 수신 즉시 턴 카운트를 차감하고 LLM을 호출하는 단순한 방식이었다. 그러나 BLUEPRINT CRITIC 검토 과정에서 다음과 같은 치명적 결함이 지적되었다.

- LLM 호출이 실패하거나(타임아웃, API 오류, Gemini 장애 등) 응답을 받지 못하는 경우에도 턴은 이미 차감된 상태로 남음
- 유저 입장에서는 정당한 응답을 받지 못했는데 하루 8턴 중 소중한 1턴을 부당하게 잃는 결과가 됨
- 특히 LLM 외부 의존성은 네트워크/서비스 장애로 실패 가능성이 상존하므로 이 결함은 발생 빈도가 낮지 않음

## Decision
턴 소비를 2단계로 분리한다.

1. **Pending 예약**: 유저 메시지가 접수되면 턴을 "사용 확정"이 아닌 "예약(pending)" 상태로 표시하고 LLM 호출을 시작한다. 이 시점에 원자적 조건부 UPDATE로 동시 요청에 의한 예산 초과를 방지한다(`TURN_IN_PROGRESS`(409) — 이미 처리 중인 턴이 있는 경우).
2. **확정**: LLM 호출이 성공적으로 완료되어 응답을 생성하면 그때 턴을 최종 확정(committed)한다. LLM 호출이 실패하면 pending을 롤백하여 유저는 턴을 잃지 않고 재시도할 수 있다.

LLM 응답 실패 시 `LLM_UNAVAILABLE`(503)을 반환하며 이때 턴 예산은 소비되지 않은 것으로 유지된다.

## Consequences

### 긍정적 영향
- LLM 호출 실패가 유저에게 불이익(턴 손실)으로 전가되지 않음 — 공정성 확보
- 동시 요청에 의한 턴 예산 초과도 원자적 조건부 UPDATE로 방지됨
- 유저 경험 관점에서 신뢰도가 높아짐 (실패해도 다시 시도하면 됨)

### 부정적 영향 / 트레이드오프
- 단순 즉시 차감 방식 대비 상태 전이가 하나 더 늘어나 구현/테스트 복잡도가 증가함
- pending 상태가 비정상적으로 오래 유지되는 경우(예: 서버 크래시로 확정/롤백 모두 실행되지 못함) 처리를 위한 방어 로직이 필요함 — 타임아웃 기반 pending 만료 또는 다음 요청 시 정리(cleanup) 로직 필요
- pending 중 동일 유저의 추가 메시지 요청은 `TURN_IN_PROGRESS`(409)로 거부되므로, 클라이언트가 이 상태를 UI에 적절히 반영해야 함

### 재검토 조건
- 없음 (본 결정은 구조적 결함 수정으로, 유지 전제)
