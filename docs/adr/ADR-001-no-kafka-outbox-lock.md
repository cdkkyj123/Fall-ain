# ADR-001: Kafka / Outbox / 분산락 / 외부 캐시(Redis) 전면 배제

## Status
Accepted

## Context
"경청이 사랑" 프로토타입은 1주일 개발 일정의 AI 연인 서비스 프로토타입이다. 일반적으로 대규모 서비스에서는 다음과 같은 인프라를 도입한다.

- Kafka 등 메시지 브로커 (이벤트 스트리밍, 외부 시스템 연동)
- Transactional Outbox 패턴 (DB 트랜잭션과 이벤트 발행의 원자성 보장)
- 분산락(Redis/Zookeeper 등) (멀티 인스턴스 환경에서의 동시성 제어)
- 외부 캐시(Redis) (세션/상태 공유, 조회 성능 향상)

그러나 이 프로토타입은 다음과 같은 특징을 가진다.

- 결제, 경매 등 고위험 동시성 도메인이 없음 (금전적 손실로 이어지는 race condition 없음)
- 외부 시스템에 이벤트를 전파할 소비자(consumer)가 없음 (다른 서비스가 이 이벤트를 구독하지 않음)
- 단일 인스턴스로 배포되며 멀티노드 간 상태 전파가 필요 없음
- 심사자가 짧은 기간 내 즉시 플레이 가능해야 하는 심사용 프로토타입

이런 상황에서 Kafka/Outbox/분산락/Redis를 도입하면 인프라 구축·운영 비용만 늘고, 정작 얻는 이득(장애 격리, 확장성, 이벤트 재처리 보장)은 이 서비스 범위에서 실현되지 않는다.

## Decision
Kafka, Outbox 패턴, 분산락, 외부 캐시(Redis)를 전면 배제한다. 대신:

- **동시성 제어**: 단일 인스턴스 배포를 전제로 JPA 낙관적락(`@Version`)과 원자적 조건부 UPDATE(예: `UPDATE ... WHERE turns_used_today < :budget`)로 대응한다.
- **이벤트 전파**: 별도 이벤트 버스 없이 서비스 메소드 직접 호출로 대체한다 (ADR-007 참조).
- **캐시**: 별도 외부 캐시 계층 없이 DB 조회 및 애플리케이션 메모리 상태로 충분히 처리한다.

## Consequences

### 긍정적 영향
- 인프라 구성 요소가 애플리케이션 서버 + MySQL만으로 단순화되어 1주 일정에 적합
- 배포/운영/장애 대응 복잡도가 크게 감소
- 로컬 개발 환경 구축이 즉시 가능 (docker-compose로 MySQL만 있으면 됨)

### 부정적 영향 / 트레이드오프
- 멀티 인스턴스로 수평 확장 시 낙관적락/조건부 UPDATE만으로는 처리량 한계가 있을 수 있음
- 향후 실제 운영 전환 시 이벤트 기반 아키텍처, 분산 캐시 재도입 검토 필요
- 서비스 간 결합도가 이벤트 버스 대비 상대적으로 높아짐 (직접 호출)

### 재검토 조건
- 멀티 인스턴스 배포가 필요해지는 시점
- 외부 시스템(알림, 분석 파이프라인 등)과의 비동기 연동이 필요해지는 시점
