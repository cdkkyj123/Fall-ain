# ADR-008: MySQL + ddl-auto 사용, Flyway 등 마이그레이션 도구 미도입

## Status
Accepted (사용자 확정)

## Context
데이터베이스로 MySQL을 사용하기로 확정했다. 일반적으로 프로덕션 환경에서는 Flyway, Liquibase 등 마이그레이션 도구를 사용해 스키마 변경 이력을 관리하고, 여러 환경(로컬/스테이징/운영) 간 스키마 일관성을 보장한다.

그러나 이 프로젝트는 1주일짜리 프로토타입이며:

- 심사 기간 중 스키마가 빈번히 바뀔 수 있고, 매번 마이그레이션 스크립트를 작성/버전관리하는 오버헤드가 개발 속도를 저해함
- 여러 환경 간 점진적 마이그레이션 이력 관리 필요성이 낮음 (심사용 단일 배포 목적)
- 마이그레이션 도구 학습/설정 비용이 1주 일정에서 상대적으로 크게 느껴짐

사용자가 이 트레이드오프를 인지한 상태에서 마이그레이션 도구 미도입을 직접 확정했다.

## Decision
Flyway, Liquibase 등 별도 마이그레이션 도구를 도입하지 않는다. 대신 Spring Boot의 `spring.jpa.hibernate.ddl-auto` 설정으로 스키마를 관리한다.

- local 환경: `create-drop` (애플리케이션 시작 시 스키마 생성, 종료 시 삭제)
- prod(심사용 배포) 환경을 포함한 모든 환경에서 동일하게 `ddl-auto` 기반 스키마 관리를 사용한다 (별도 마이그레이션 스크립트 없음)

## Consequences

### 긍정적 영향
- 엔티티 클래스만 수정하면 스키마가 자동으로 반영되어 개발 속도가 크게 향상됨
- 마이그레이션 스크립트 작성/버전관리/도구 설정 비용이 전혀 없음
- 1주 일정에서 스키마가 자주 바뀌는 프로토타이핑 단계에 적합함

### 부정적 영향 / 트레이드오프
- **prod 환경까지 `ddl-auto`를 사용하는 것은 일반적으로 위험한 관행**이다. 배포마다 스키마가 예기치 않게 변경되거나 데이터 손실이 발생할 수 있음. 이 프로토타입은 심사용 단발성 배포이며 보존해야 할 운영 데이터가 없다는 전제하에만 허용 가능한 리스크임.
- 스키마 변경 이력이 Git 커밋 로그 외에는 별도로 추적되지 않음
- 여러 개발자가 동시에 작업할 경우 로컬 스키마 상태가 서로 달라질 수 있음 (엔티티만 맞으면 자동 동기화되므로 실질적 영향은 제한적)
- 향후 실제 운영 서비스로 전환 시 Flyway 등 마이그레이션 도구 도입이 반드시 필요함 — 기존 데이터를 보존한 채 스키마를 점진적으로 변경할 수단이 없기 때문

### 재검토 조건
- 프로토타입이 실제 운영 서비스로 전환되어 보존해야 할 데이터가 발생하는 시점 (필수 재검토)
- 여러 개발자가 병렬로 스키마를 변경하며 충돌이 잦아지는 시점
