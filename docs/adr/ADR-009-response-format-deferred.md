# ADR-009: 성공 응답(2xx) 공통 포맷은 BACKEND 구현 단계로 위임

## Status
Accepted (사용자 확정)

## Context
API 응답 포맷을 설계할 때 흔히 모든 성공 응답을 공통 래퍼(예: `{success, data, meta}` 형태)로 감쌀지, 아니면 각 엔드포인트의 리소스를 그대로 반환할지 결정해야 한다. 이 결정은 프론트엔드 클라이언트 구현 방식과 얽혀 있고, 어느 쪽이 이 프로젝트에 더 적합한지는 BACKEND 구현 시작 시점에 실제 리소스 형태를 보며 정하는 것이 더 실용적이라고 판단되었다.

반면 에러 응답 포맷은 클라이언트의 에러 핸들링 로직과 직결되고 API 명세 전반에 걸쳐 일관되게 적용되어야 하므로 BLUEPRINT 단계에서 미리 확정할 필요가 있었다.

## Decision
- **에러 응답 포맷**: BLUEPRINT에서 확정. 모든 에러는 `{code, message}` 형태로 반환하며, 에러코드-HTTP 상태코드 매핑도 BLUEPRINT에서 고정한다 (API.md 참조).
- **성공 응답(2xx) 포맷**: 지금 확정하지 않는다. Phase 3b BACKEND 에이전트 구현 시점에 각 엔드포인트의 실제 반환 리소스 구조를 보며 재량으로 결정한다. 단, 결정된 포맷은 프로젝트 전체에서 일관되게 적용해야 하며, `docs/api/API.md`에 구현 완료 후 반영되어야 한다.

## Consequences

### 긍정적 영향
- 성공 응답 구조를 설계 단계의 추측이 아닌 실제 구현 시점의 리소스 형태를 보고 결정할 수 있음
- BLUEPRINT 단계에서 불필요한 논의를 줄이고 핵심 아키텍처 결정(ADR-001~008)에 집중 가능

### 부정적 영향 / 트레이드오프
- BACKEND 구현 전까지 프론트엔드가 정확한 성공 응답 스키마를 알 수 없어 병렬 작업 시 초반 불확실성이 존재함
- BACKEND 에이전트의 재량 범위가 넓어, 엔드포인트별로 일관성 없는 포맷이 나올 위험이 있음 — 구현 시 명시적으로 프로젝트 전체 일관성을 지켜야 함
- API.md 문서가 이 부분에 한해 Phase 3b 완료 전까지는 미완 상태로 남음 (Phase 4.5 DOCS에서 최종 반영 필요)

### 재검토 조건
- Phase 3b BACKEND 구현 완료 시점에 성공 응답 포맷이 확정되면 즉시 본 ADR의 Status를 "Superseded"로 갱신하고 확정된 포맷을 API.md에 반영해야 함
